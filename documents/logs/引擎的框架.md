# 引擎的执行流程
引擎在初始化阶段首先明确的问题:
1. 不同的系统如何选择对应的 EntryPoint
2. 谁负责初始化 Engine Runtime
3. 谁负责控制 Game 的生命周期

对于不同的 Entry Provider, 大致可以分成两种: Native Provider 和 Middleware Provider. 例如:
- Native Provider: Windows, 各种 Linux 发行版, macOS
- Middleware Provider: SDL3, GLFW

由不同的 Entry Provider 提供的 Entry 最终会统一的进入 `EngineMain(argc, argv)`, 然后将输入的参数 传入 `EngineMain(argc, argv)`, 再由 `EngineMain(argc, argv)` 构造出 `GenericPlatform` 对象, 该对象会负责启动 Engine Runtime.

所以其目录结构大致如下(仅示例):
```text
Engine/
└── Launch/
    ├── EngineMain.cpp
    │
    └── Entry/
        ├── Native/
        │   ├── Windows.cpp
        │   └── MacOS.cpp
        │
        └── SDL/
            └── Main.cpp
```



# 引擎结构
sources/engine 是引擎的核心模块, 其分成以下结构
- modules 下的每一个模块都代表了引擎中的一个功能, 他们可以在外部被成功构建和使用(但需要core), 但是并非最优解甚至可能出现功能缺失. 因为其设计的起点是引擎优先而不是通用性
- core 下的每一个模块其类似于标准库的定位(但依旧不以通用为优先), 其仅仅是提供一种容器, 包装器等等. 其功能规模会非常小, 核心在与仅依赖标准库和操作系统API.
- launcher: 启动器, 其负责确定 entry 创建 虚拟控制台 CommandLine 对象并初始化整个引擎(包括编辑器)拉起引擎运行时. 在借由引擎运行时加载游戏并控制游戏的生命周期
- runtime: 引擎的运行时

这里主要是想区分 modules 和 engine/core 的定位.


# Extra
> [!note] 引擎和游戏的关系
> 在面对引擎和游戏的关系这一问题上, 往往有两种不同的答案:
> 1. Game 是主体(之后简称 [Game]): 引擎本质是游戏的一个公共代码库, 游戏在启动之后链接该库并自定义自己的游戏逻辑
> 2. Engine 是主体(之后简称 [Engine]):游戏是引擎这个运行环境的执行实体, 其生命周期由引擎控制.
>
> 基于 [Game] 开发的相对被广泛认可的库是 raylib, 基于 [Engine] 开发的引擎最被人熟知的可能是虚幻引擎
> 当然由于使用 [Game] 的思路的游戏开发者往往其项目也不会公开, 所以 [Game] 这一思路的实际使用者可能比预估的要多很多
> 
> 但是现代引擎更多的使用 [Engine] 这种思路开发自己的引擎. 其更多的考虑了以下的情况:
> 1. 有清晰的构建边界, 引擎只需要编译一次就可以导出使用. 而使用 [Game] 这一思路则往往需要和游戏本体一起编译. 同时引擎开发者可以把所有需要的库都提前放入引擎的运行时中, 即游戏本体几乎只需要依赖引擎, 不需要自己手动引入其他依赖.
> 2. 引擎更容易构建虚拟环境以简化开发. 例如引擎本体使用 C++ 开发, 但游戏本身可以使用 Lua, Ts, C# 等语言通过绑定引擎API来避免使用C++. 如果使用 [Game] 则很多情况是要与引擎使用同一种语言
> 3. 跨平台优势, 对于市面上的常见平台可以引擎可以通过构建系统动态选择入口来避免让开发者自己封装系统入口. [Game] 这一思路想实现这个方式则相对复杂, 可以参考 SDL 的实现.
> 
> 本质上 [Game] 这种方案中的引擎只是一些功能的提供者, 是一个真正意义上的公共代码库. 其可能只包含例如渲染, 物理, 动画等功能, 但是对于具体使用这些功能需要开发者自己协调使用. [Engine] 本质上提供的是一种虚拟环境, 其完全控制了游戏内对象的生命周期, 使得开发者需要听从引擎定义的规则即可.
